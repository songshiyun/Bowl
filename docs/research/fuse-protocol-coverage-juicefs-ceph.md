## 核心结论摘要

1. **两者均未全部适配 Linux FUSE 内核协议（`enum fuse_opcode` 共 50+ 个操作码）**：
   - **JuiceFS** 在 [`pkg/fuse/fuse.go`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/fuse/fuse.go#L39-L466) 的 `fileSystem` 中显式重写了 **31 个** `RawFileSystem` 方法（覆盖 **33 个** FUSE 内核操作码，因 `Rename` 同时处理 `_OP_RENAME` 与 `_OP_RENAME2`、`Create` 同时处理 `_OP_CREATE` 与 `_OP_TMPFILE`），另有 **6 个**协议框架操作码（`INIT`、`DESTROY`、`INTERRUPT`、`FORGET`、`BATCH_FORGET`、`NOTIFY_REPLY`）由 `go-fuse` 框架层直接接管；其余 **13+ 个**操作码（`ACCESS`、`FSYNCDIR`、`BMAP`、`POLL`、`LSEEK`、`SETUPMAPPING`、`REMOVEMAPPING`、`SYNCFS`、`STATX` 等）直接返回 `ENOSYS`。
   - **Ceph (`ceph-fuse`)** 在 [`src/client/fuse_ll.cc`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/fuse_ll.cc#L1513-L1565) 的 `fuse_ll_oper` 中注册了 **32 个** `fuse_lowlevel_ops` 回调，并通过 `fuse_req_interrupt_func` 动态绑定 `INTERRUPT`（共覆盖 **34 个** FUSE 内核操作码，其中 `setlk` 回调通过 `sleep` 参数同时服务 `FUSE_SETLK` 与 `FUSE_SETLKW`）；显式将 `destroy`、`bmap`、`poll`、`write_buf`、`retrieve_reply`、`forget_multi` 置为 `0`，且未注册 `readdirplus`、`copy_file_range`、`lseek`、`tmpfile`、`statx`、`syncfs` 等回调。
2. **已适配协议的“客户端本地处理 vs 远端元数据服务”分层高度清晰，但两套架构的分工哲学截然不同**：
   - **JuiceFS（无状态/胖元数据引擎客户端）**：客户端不维护跨请求的强一致 Inode 锁租约，`Forget`/`BatchForget` 在客户端完全为空操作；`OpenDir` 仅在 VFS 内存分配 `FileHandle`，首次 `ReadDir`/`ReadDirPlus` 才调用 `Meta.NewDirHandler` 一次性拉取目录全量 `Entry` 列表并在客户端内存分页，`ReleaseDir` 仅清理内存句柄；`Flush`/`Fsync` 若无脏数据缓存刷盘，则**完全不请求元数据服务**（在客户端直接返回 `0`）。
   - **Ceph（基于 Capability 与 Lease 的重状态客户端）**：客户端通过 `CEPH_CAP_*` 能力掩码与目录项租约（Lease）将大量读操作与部分写操作短路在客户端本地内存完成。当持有有效租约或 `CEPH_CAP_*` 时，`Lookup`、`GetAttr`、`Access`、`Readlink`、`GetXattr`、`ListXattr`、`Open`、`SetAttr`（`size`/`mtime`）、`Fallocate`（扩展大小）均可**零 MDS RPC** 在客户端本地完成；`OpenDir`/`ReleaseDir`、`Flush`、`Forget` 纯属客户端内存操作；甚至 `StatFs` 也不请求 MDS，而是由客户端通过 `Objecter` 直接向 RADOS Monitor/OSD 查询池容量（`CEPH_OSD_OP_STATFS`）并结合本地 Quota Root 的 `rstat` 缓存合成。
3. **对照 Bowl 的 28 个 RPC 接口**：
   - Bowl 的 28 个 RPC 精准覆盖了 POSIX 命名空间、Inode `Attribute`、`FileHandle`、`Xattr` 与字节范围 `FileLock` 的核心元数据集合。
   - **Bowl 放入服务端 RPC、而 JuiceFS/Ceph 下沉到客户端内存处理的操作**：`OpenDir` 与 `ReleaseDir`（JuiceFS/Ceph 均无对应的远端 `OpenDir`/`ReleaseDir` 元数据 RPC，目录遍历游标生命周期由客户端内存维护）、无数据落盘变更时的 `Flush` 与 `Fsync`（JuiceFS 在无脏切片时完全不发元数据 RPC；Ceph 的 `Flush` 仅读取本地异步刷盘错误码）。
   - **JuiceFS / Ceph 在元数据层额外实现、而 Bowl 当前未定义 RPC 的操作**：文件系统容量统计 `StatFs`（JuiceFS `Meta.StatFS`）、增强重命名标志 `Rename2`（JuiceFS `Meta.Rename` 支持 `RENAME_NOREPLACE` / `RENAME_EXCHANGE`）、匿名临时文件 `TmpFile`（JuiceFS 定制 `go-fuse` 对接 `_OP_TMPFILE`）、服务端零拷贝克隆 `CopyFileRange`（JuiceFS `Meta.CopyFileRange`）、文件属性控制 `Ioctl`（`FS_IOC_GETFLAGS` / `FS_IOC_SETFLAGS`），以及通过父 Inode 反向解析路径/父节点的 `GetParents` / `CEPH_MDS_OP_LOOKUPPARENT`。

### 1.2 未适配的 FUSE 协议及其架构原因分析

#### （1）两者共同未适配的协议
1. **`FUSE_BMAP (37)`**：
   - **原因**：`bmap`（将文件逻辑块映射为底层块设备物理扇区号，供 `FIBMAP` ioctl 或旧式 swapfile 使用）仅对本地块设备文件系统有意义。JuiceFS 将数据切分为 Chunk/Slice 存储在对象存储中，Ceph 将文件条带化为 RADOS 对象，均不存在单块设备的物理块号映射。
2. **`FUSE_POLL (40)`**：
   - **原因**：普通 POSIX 文件与目录在内核 VFS 层默认总是立即就绪（可读/可写）；FIFO（命名管道）与 UNIX 域套接字在 `Mknod` 创建出特殊类型 Inode 后，其收发队列与 `poll`/`epoll` 唤醒完全由客户端主机本地 Linux 内核（`pipe_fifo_fops` / `unix_stream_ops`）接管，无需也不应跨网络向分布式文件系统守护进程轮询。
3. **`FUSE_SETUPMAPPING (48)` 与 `FUSE_REMOVEMAPPING (49)`**：
   - **原因**：这是 `virtio-fs` 专用的 DAX（Direct Access）宿主机页面缓存直接映射协议，仅在使用 QEMU/KVM 虚拟化共享内存窗口（Virtio PCI BAR）时生效，传统 `/dev/fuse` 守护进程无法使用。
4. **`FUSE_LSEEK (46)`**：
   - **原因**：用于加速稀疏文件的 `SEEK_DATA` / `SEEK_HOLE`。当守护进程返回 `ENOSYS` 后，Linux FUSE 内核模块会自动置位 `fc->no_lseek = 1`，并将整個文件 `[0, i_size)` 视为数据区（`SEEK_DATA` 直接返回原偏移，`SEEK_HOLE` 直接返回 `i_size`），完全符合 POSIX 规范且避免了去遍历远端对象/Slice 索引的开销。
5. **`FUSE_STATX (52)` 与 `FUSE_SYNCFS (50)`**：
   - **原因**：Linux 5.18+ / 6.x 较新的扩展。返回 `ENOSYS` 后，内核在 `statx()` 系统调用中自动回退为发送 `FUSE_GETATTR (3)`，在 `syncfs()` 中回退为刷写内核自身的脏页缓存（Page Cache）并下发 `FUSE_WRITE` / `FUSE_FSYNC`。

#### （2）JuiceFS 特有未适配项及原因
1. **`FUSE_ACCESS (34)`**：
   - **源码证据**：尽管 `vfs.VFS` 实现了 [`Access`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs_unix.go#L77-L99)，但 [`pkg/fuse/fuse.go`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/fuse/fuse.go#L39-L466) 的 `fileSystem` **故意没有实现 `Access` 方法**，从而继承 [`defaultRawFileSystem.Access`](file:///Users/fanxing/go/pkg/mod/github.com/juicedata/go-fuse/v2@v2.1.1-0.20260819084346-22b3157c2d7f/fuse/defaultraw.go#L100-L102) 返回 `ENOSYS`。
   - **原因**：JuiceFS 挂载时默认启用 `-o default_permissions`（见 [`fuse.go`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/fuse/fuse.go#L524-L526)），让 Linux 内核 VFS 直接利用缓存的 Inode `Attribute` 与 POSIX ACL (`system.posix_acl_access`) 在内核态完成权限校验；即使启用了 `--non-default-permission`，每个具体操作（如 `Open`、`Lookup`、`Mknod`）在 VFS/Meta 层内部也会主动调用 `ctx.CheckPermission()`。对 `FUSE_ACCESS` 返回一次 `ENOSYS` 后，Linux 内核会永久置位 `fc->no_access = 1`，彻底消除每次路径操作前多余的 `FUSE_ACCESS` 用户态往返。
2. **`FUSE_FSYNCDIR (30)`**：
   - **源码证据**：继承 [`defaultRawFileSystem.FsyncDir`](file:///Users/fanxing/go/pkg/mod/github.com/juicedata/go-fuse/v2@v2.1.1-0.20260819084346-22b3157c2d7f/fuse/defaultraw.go#L154-L156) 返回 `ENOSYS`。
   - **原因**：JuiceFS 的所有目录变更操作（`Mkdir`、`Mknod`、`Unlink`、`Rmdir`、`Rename`、`Link`、`Symlink`）在返回客户端前均已在底层数据库/KV 引擎中通过事务（[`dbMeta.txn`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/sql.go#L1320-L1357)）同步提交持久化，客户端不存在未落盘的目录脏缓冲区。

#### （3）Ceph (`ceph-fuse`) 特有未适配项及原因
1. **`FUSE_READDIRPLUS (44)`**：
   - **源码证据**：[`fuse_ll_oper`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/fuse_ll.cc#L1536-L1538) 仅注册了 `readdir: fuse_ll_readdir`，未注册 libfuse3 的 `readdirplus` 回调。
   - **原因**：Ceph 的 MDS `CEPH_MDS_OP_READDIR`（[`Client::readdir_r_cb`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L10103-L10139)）本身在网络协议层就是天然的“ReadDirPlus”——MDS 在一次 `CEPH_MDS_OP_READDIR` 响应中会将目录下所有子项的 `Inode` 完整元数据、能力（Capabilities）及目录项租约（Dentry Lease）一并下发并预填充到 `ceph-fuse` 进程内的 `Client` 缓存中。当内核紧接着发起 `FUSE_LOOKUP` / `FUSE_GETATTR` 时，`ceph-fuse` 直接在进程内存的 `dir->dir->dentries` 中命中有效租约（[`Client::_lookup`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L7905-L7930)）并毫秒级返回，无需再次访问 MDS。
2. **`FUSE_RENAME2 (45)` 的特殊标志（`RENAME_EXCHANGE` / `RENAME_NOREPLACE`）**：
   - **源码证据**：[`fuse_ll_rename`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/fuse_ll.cc#L768-L775) 虽然使用了 libfuse3 带 `unsigned int flags` 的签名，但首行即判断 `if (flags) { fuse_reply_err(req, EINVAL); return; }`。
   - **原因**：Ceph MDS 的 `CEPH_MDS_OP_RENAME` 协议头早期未支持 `RENAME_EXCHANGE` 等原子交换标志，因此在 FUSE 层直接拦截非零 `flags`。
3. **`FUSE_COPY_FILE_RANGE (47)` 与 `FUSE_TMPFILE (51)`**：
   - **原因**：`ceph-fuse` 基于较早的 libfuse 兼容接口演进，尚未在 `fuse_ll_oper` 中暴露 `copy_file_range` 与 `tmpfile` 回调（由内核回退为 `read`+`write` 或用户态临时文件创建）。

### 2.2 重点深挖：哪些操作在客户端直接处理而无需请求远端元数据服务？

#### （1）JuiceFS 客户端直接处理（或条件短路）的 6 类操作
1. **`Forget` 与 `BatchForget`（100% 客户端空操作）**：
   - 在 [`defaultRawFileSystem.Forget`](file:///Users/fanxing/go/pkg/mod/github.com/juicedata/go-fuse/v2@v2.1.1-0.20260819084346-22b3157c2d7f/fuse/defaultraw.go#L37-L38) 中方法体为空 `{}`。因为 JuiceFS 直接将数据库中持久化的 64 位 `Ino` 作为 FUSE 协议的 `NodeId` 返回给内核，客户端不需要维护 `NodeId -> 内存对象指针` 的映射表，因此内核回收 `dentry` 时下发的 `FORGET` 无需任何处理。
2. **`OpenDir` 与 `ReleaseDir`（100% 客户端内存句柄管理）**：
   - [`VFS.Opendir`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs.go#L807-L821) 仅调用 `v.newHandle(ino, false, flags)` 在进程内存的 `hanleMap` 中分配一个 `uint64` `fh`（仅在显式关闭 `DefaultPermission` 时才调用一次 `Meta.Access`）。
   - [`VFS.Releasedir`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs.go#L886-L896) 仅释放 `h.dh` 内存切片并调用 `v.releaseHandle(ino, fh)`。`Meta` 接口（[`interface.go`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L397-L473)）中**根本不存在 `OpenDir` 或 `ReleaseDir` 方法**。
3. **`ReadDir` / `ReadDirPlus` 的后续分页请求（客户端内存切片迭代）**：

### 3.2 JuiceFS 与 Ceph 有意省略或下沉到客户端实现、而 Bowl 定义为服务端 RPC 的操作

1. **目录会话生命周期（`OpenDir` 与 `ReleaseDir`）**：
   - **Bowl 现状**：在 [`storage.proto`](file:///Users/fanxing/code/starsrc/bowl/proto/storage/v1/storage.proto#L117-L123) 中将 `OpenDir` 和 `ReleaseDir` 定义为访问远端存储服务的独立 RPC，在服务端数据库/状态层分配和销毁目录 `FileHandle`。
   - **JuiceFS 与 Ceph 的做法**：两者均将 `OpenDir` 和 `ReleaseDir` **100% 下沉在 FUSE 客户端本地内存处理**（JuiceFS [`VFS.Opendir`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs.go#L807-L821) / [`VFS.Releasedir`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs.go#L886-L896)；Ceph [`Client::_opendir`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L9778-L9786) / [`Client::_closedir`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L9800-L9817)）。
   - **设计考量**：POSIX 目录遍历（如 `ls`、`find`、`fts_read`）极度高频，且目录无法像普通文件那样在 `Unlink` 后维持 `Orphan Inode` 延迟删除语义（非空目录禁止 `Rmdir`，空目录 `Rmdir` 后无需保留数据块）。因此，远端元数据服务完全不需要感知“某个客户端当前打开了哪个目录句柄”，只需提供无状态的 `ReadDir(ino, offset/cursor, limit)`，将 `OpenDir`/`ReleaseDir` 留在 FUSE 客户端本地内存即可直接省去每次遍历目录时的 **2 次跨网络 RPC 往返**。
2. **文件句柄刷写（`Flush` 与 `Fsync`）**：
   - **Bowl 现状**：在 [`storage.proto`](file:///Users/fanxing/code/starsrc/bowl/proto/storage/v1/storage.proto#L97-L104) 中定义了 `Flush` 与 `Fsync` RPC。
   - **JuiceFS 与 Ceph 的做法**：在 FUSE 中，进程每次 `close(fd)`（含 `dup`/`fork` 产生的多个文件描述符副本关闭）都会触发一次 `FUSE_FLUSH`。JuiceFS 在 [`VFS.Flush`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/vfs/vfs.go#L782-L805) 中若发现该 `FileHandle` 无未刷盘的脏数据缓冲（例如只读打开的文件），直接在客户端本地返回 `0`，绝不发远端 RPC；Ceph 的 [`Client::_flush(Fh*)`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L13110-L13122) 更是只检查本地 `f->take_async_err()`。
   - **设计启示**：Bowl 的 FUSE 客户端适配层在调用远端 `Flush` / `Fsync` RPC 前，应当根据本地 `FileHandle` 的打开标志（只读 vs 可写）及是否存在未提交脏状态进行短路过滤，避免每个只读文件 `close()` 都产生一次无意义的远端 `Flush` RPC。
3. **`SetLk` 与 `SetLkw` 的协议合并**：
   - **Bowl 现状**：将非阻塞锁 `SetLk` ([L183](file:///Users/fanxing/code/starsrc/bowl/proto/storage/v1/storage.proto#L183)) 与阻塞锁 `SetLkw` ([L190](file:///Users/fanxing/code/starsrc/bowl/proto/storage/v1/storage.proto#L190)) 拆分为两个独立 RPC。
   - **JuiceFS 与 Ceph 的做法**：两者在元数据接口层均合并为单一原语（JuiceFS `Meta.Setlk(..., block bool, ...)`，[`interface.go`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L457)；Ceph `CEPH_MDS_OP_SETFILELOCK` 携带 `wait = sleep` 字段，[`Client.cc`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/Client.cc#L13788)）。

### 3.3 JuiceFS 与 Ceph 在元数据层额外实现、而 Bowl 当前未涵盖的操作

2. **`Rename2`（带标志位的增强重命名，`FUSE_RENAME2 = 45`）与 `TmpFile`（匿名临时文件，`FUSE_TMPFILE = 51`）**：

   - **Ceph**：在 [`fuse_ll_rename`](file:///Users/fanxing/code/other/filesystem/ceph/src/client/fuse_ll.cc#L768-L775) 中对非零 `flags` 直接返回 `EINVAL`，未支持 `FUSE_TMPFILE`。
   - **对 Bowl 的影响**：Bowl 当前 [`RenameRequest`](file:///Users/fanxing/code/starsrc/bowl/proto/storage/v1/storage.proto#L553-L589) 尚无 `flags` 字段，亦未提供 `TmpFile` RPC（注：对于 BSD `flock(2)`，Bowl 已在 [ADR-0012](file:///Users/fanxing/code/starsrc/bowl/docs/adr/0012-fuse-file-locks-and-session-lease-semantics.md) 中通过 `GetLk`/`SetLk`/`SetLkw` 的 `lk_flags = FUSE_LK_FLOCK` 完整实现，与 JuiceFS/Ceph 能力对齐）。
3. **`CopyFileRange`（服务端零拷贝数据段克隆，`FUSE_COPY_FILE_RANGE = 47`）**：
   - **JuiceFS**：[`Meta.CopyFileRange`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L442)（实现见 [`dbMeta.CopyFileRange`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/sql.go#L3565-L3699)），仅在元数据层复制源文件的 Slice 描述符并递增 Chunk 引用计数，实现 $O(1)$ 零数据搬运拷贝（需结合 M2 数据分块层实现）。
4. **基于客户端 Session 的孤儿文件（`Orphan Inode`）崩溃兜底回收**：
   - **JuiceFS**：`Meta` 接口定义了完整的会话生命周期 [`NewSession`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L379)、[`CloseSession`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L381)、[`CleanStaleSessions`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/base.go#L993-L1010)（SQL 实现见 [`dbMeta.doCleanStaleSession`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/sql.go#L3307-L3368)）。当某个客户端进程崩溃失联、会话心跳超时后，其他节点或清理任务不仅会清理该 `sid` 下残留的 `jfs_flock` / `jfs_plock` 锁记录，还会自动清理 `jfs_sustained`（即已 `Unlink` 但客户端崩溃前未下发 `Release` 的 `Orphan Inode`）。
   - **Ceph**：MDS 通过 `CEPH_MSG_CLIENT_SESSION` 维护有状态会话，客户端超时被驱逐（Evict）时自动回收其持有的 Capabilities、`FileLock` 与 Stray（Orphan）Inode 引用。
   - **对 Bowl 的影响**：Bowl 在 [ADR-0012](file:///Users/fanxing/code/starsrc/bowl/docs/adr/0012-fuse-file-locks-and-session-lease-semantics.md) 中已为 `file_locks` 绑定了 `client_sessions` 租约级联清理，但 [ADR-0009](file:///Users/fanxing/code/starsrc/bowl/docs/adr/0009-fuse-file-handle-lifecycle-and-orphan-reclamation.md) 的 `file_handles` 尚未绑定 `session_id`，若客户端在持有 `unlink-whilst-open` 句柄期间崩溃未发送 `Release`，该 `Orphan Inode` 将无法自动触发物理回收。
5. **反向路径解析与按 Inode 句柄查找（`GetParents` / `LOOKUPINO` / `LOOKUPPARENT`）**：
   - **JuiceFS**：[`Meta.GetParents`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L462) 与 [`Meta.GetPaths`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/base.go#L2387-L2469)。
   - **Ceph**：`CEPH_MDS_OP_LOOKUPHASH (0x00102)`、`CEPH_MDS_OP_LOOKUPPARENT (0x00103)`、`CEPH_MDS_OP_LOOKUPINO (0x00104)`、`CEPH_MDS_OP_LOOKUPNAME (0x00105)`（[`ceph_fs.h`](file:///Users/fanxing/code/other/filesystem/ceph/src/include/ceph_fs.h#L405-L408)），用于在客户端缓存失效、子目录挂载或 NFS 文件句柄导出场景下从任意 Inode 反向定位父目录及目录项名称。
6. **数据面 Slice / Extent 映射接口（`Read` / `Write` / `NewSlice` / `Truncate`）**：
   - **JuiceFS**：由于 JuiceFS 采用“元数据引擎管理 Chunk->Slice 映射 + 对象存储保存 Slice 数据块”的架构，`Meta` 接口包含 [`NewSlice`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L436)、[`Read`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L438)（读取指定 Chunk 的 Slice 列表）、[`Write`](file:///Users/fanxing/code/other/filesystem/juicefs/pkg/meta/interface.go#L439)（记录新写入的 Slice 映射并更新 Inode 大小与 `mtime`）。
   - **Ceph**：采用基于固定条带布局（`file_layout_t`：`stripe_unit`、`stripe_count`、`object_size`、`pool_id`）的确定性哈希算法，客户端拿到 Inode 上的 `layout` 后即可自行计算出任意偏移对应的 RADOS 对象 OID（`<ino>.<obj_idx>`），因此读写数据块时**无需向 MDS 查询或提交块映射列表**。
